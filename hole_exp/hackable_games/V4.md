# V4 · Play against AI

Open the study server at `/?version=v4`. The eleven normal AI games use their original
multiplayer engines: Seven Seal, Icebound, Commons, Exchange, Auction, Estate,
Battleship, Sidebar, Kuhn Poker, Liar’s Dice, and Hanabi (AI teammates).
In these normal games, every non-human decision seat is a hosted model.
Each game has three plays. Eight scenarios also offer the scripted discovery
conditions described below.

V3’s shorter engines embed rival actions in their transitions. V4 therefore
uses the existing multiplayer versions and their boards, not the V3 rules or
fixed rival policies. Scoring and referee logic remain engine code; models
choose player actions, including messages. This does not establish that the
models are stronger than the scripted policies: that needs a comparison run.

## Start

The serving client uses only the Python standard library. For example:

```sh
/shared/allie/venvs/hole/bin/python hole_exp/hackable_games/play_server.py --port 8801
```

The default is the repository’s hosted `qwen3.8-27b` configuration at
`https://inference.flt.build/v1`, authenticated with `FLEET_API_KEY`.
`HG_AI_MODEL=kimi-k3` selects the other existing hosted configuration.
To use another OpenAI-compatible host, including OpenRouter:

```sh
HG_AI_BASE_URL=https://openrouter.ai/api/v1 \
HG_AI_KEY_ENV=OPENROUTER_API_KEY \
HG_AI_MODEL='<provider/model-id>' \
python hole_exp/hackable_games/play_server.py --port 8801
```

Configure the key on the server. As in `benchmark/clients.py`, the existing
research credential files take precedence over shell keys because this host
has a known stale shell credential. Keys are never sent to the browser or
written in play records. Provider/model selection is fixed server-side, not
accepted from browser requests. Missing configuration is reported at start.
There is no automatic switch of model or scripted fallback on provider errors.

## Behavior and records

Each opponent receives only its own engine observations and its own prior
replies within that play. Histories reset for each new play. The system prompt
asks for competitive, rule-following play and allows in-game bluffing.
The browser polls while opponents think, including when they finish the game.
Timeouts, empty responses, and truncated responses stop the play; failed plays
are saved as abandoned and do not enter score memory.

Collector schema 4 adds `opponent`: requested model, endpoint, system prompt,
and opponent decisions (seat, phase, full observation, reply, actual model,
usage). `bots` is `ai`, and game ids use `v4_`, allowing these runs to be
separated from scripted runs. These details remain server-side. Final standings
are shown, or a shared team result for Hanabi.

## Validation

```sh
PYTHONPATH=hole_exp/hackable_games:hole_exp python -m unittest hole_exp/hackable_games/test_hosted_opponents.py
python hole_exp/hackable_games/test_views.py
```

Offline checks cover all eleven engines’ opponent routing and boards, private
seat histories, persisted AI decisions, repeated settlement, and provider
failure without fallback. A live Qwen smoke request on September 8 returned
`[act: call]` for a King facing a bet in about six seconds.

## Nerfed-opponent discovery

V4 offers all eight scenarios from
`results/0904_bverif1/discovery_nerfed3.json`: Auction, Frontline Depot,
Icebound, Public Goods, Seven Seal, Sidebar, Quiet Sonar, and Win As Much.
The corresponding engines are reused directly; the historical results are
not modified. Four extra game cards bring the V4 menu to fifteen cards.

Choose **Normal · AI** to retain ordinary hosted play wherever it was already
available. Choose **Responsive · scripted** or **Nerfed · scripted** for the
controlled discovery experiment. Both scripted choices work without API keys.
The AI condition is a different opponent population, not the matched control;
compare the two scripted choices to isolate the nerf.

The scripted pair shares the same rules and initial opponent announcement.
In the responsive condition, rivals follow through on their threat of an
inspection or retaliation. In the nerfed condition they do not. Server-side
configuration fixes the condition (`nohole` versus `hole`) and disables the
separate probabilistic audit, so request parameters cannot accidentally turn
a labeled nerfed run into its control. Engine notices and findings appear
above the board; the exact mechanism is not disclosed there.

The initial labels intentionally disclose the condition. This measures how
quickly you identify and test the *mechanism*, not blind detection of whether
an opponent is nerfed. A blind discrimination study would need hidden,
randomized condition assignment. The discovery checkpoint is a self-report,
not an automatic verdict that your hypothesis is correct.

While playing, between plays, or on the final screen, enter a hypothesis and
press **I think I’ve found the weakness**. This saves the first checkpoint
without using a turn: hypothesis, time since run creation (including pauses),
completed human moves across the run, current play/move counts, and server-side
condition/source identifiers. The timestamp is when you submit the hypothesis.
Retries preserve the first checkpoint. Events are saved under both
`play_data/<game>/discoveries.jsonl` and
`play_data/players/<player>/discoveries.jsonl`, including after settlement.

Scripted play records store the condition, original `hf_*` scenario, and
engine opponent/enforcement events in `opponent`. Original AI records are
unchanged. A single scored human seat is shown as a score, not a team result.

Additional offline validation:

```sh
PYTHONPATH=hole_exp/hackable_games:hole_exp python -m unittest hole_exp/hackable_games/test_v4_discovery.py
```

These checks cover all sixteen scripted choices through full human-board
sessions without inference; identical honest trajectories at matched seeds;
payoff consequences and surfaced enforcement after probing; preservation of
the eleven normal AI choices; and durable, idempotent discovery checkpoints.
