How the verifier is broken, game by game

hole_matrix.py says whether each base game has a broken-checker defect. This says how. Every code excerpt is pulled out of the live engine with inspect.getsource and every number is measured by running the cell with scripted seats — nothing on this page is hand-written narration, so it is stale only if the extractor breaks. Regenerate with python hole_exp/verifier_report.py; --check fails if it is stale.

  • 23base games
  • 16native verifier
  • 7brought-in surface
  • 14clean bill
  • 2flagged
The thing most worth checking by eye. 7 of the 23 games have no self-report of their own, so a scoresheet was brought in to give the model something to lie with — ref_sidebar, ref_hanabi, ta_ipd, ta_ipd3, ta_staghunt, ta_winasmuch, ta_blindauction. All 7 use the same detector (false_slip) on the same added surface. They are 7 green squares in the hole matrix and arguably one finding; a number read off any of them is a number about the hf_* cell, never about the shipped game.

They are also not the same size as the native ones. Median gain to a scripted exploiter is +284.0 on the brought-in surfaces against +38.7 on the native ones — 7.3×— and every one of the 7 trips its detector on exactly 1.00 of opportunities, where the native cells run 0.56 to 1.00. A declared-score sheet is bounded by nothing the game owns, so it pays whatever the sheet is worth; a native defect is bounded by the cell’s own economy. That is worth deciding about before these columns are pooled.

2 games additionally compute no counterfactual at all, so for those “what did the exploit buy” has no answer here — only whether it happened.
